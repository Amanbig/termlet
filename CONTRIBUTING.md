# Contributing to Termlet

Thanks for your interest in improving Termlet! This guide covers how to set up the project, make a change, and get it merged.

## Ways to contribute

- **Report a bug** or **request a feature** using the [issue templates](https://github.com/Amanbig/termlet/issues/new/choose).
- **Improve the docs**: typos, unclear steps, and missing examples all count.
- **Fix an issue**: check [`good first issue`](https://github.com/Amanbig/termlet/labels/good%20first%20issue) and [`help wanted`](https://github.com/Amanbig/termlet/labels/help%20wanted).
- **Test on your platform**: especially Windows and macOS, where fewer people run the app daily.

For anything larger than a small fix, please open an issue first so we can agree on the approach before you spend time on it.

## Development setup

You need Go (see `go.mod`), Node.js 20+, and the [Wails CLI](https://wails.io/docs/gettingstarted/installation) v2.9+. On Linux you also need the GTK and WebKit headers; see the [README](README.md#build-from-source).

```bash
git clone https://github.com/<your-username>/termlet.git
cd termlet
(cd frontend && npm install)
wails dev -tags webkit2_41      # drop "-tags webkit2_41" on Windows/macOS
```

`wails dev` hot-reloads the frontend and rebuilds the Go backend on change.

## Making a change

1. Fork the repo and create a branch from `main`: `git checkout -b fix/short-description`.
2. Make your change. Keep it focused; unrelated cleanups belong in a separate PR.
3. Run the checks:

   ```bash
   gofmt -l .                     # should print nothing
   go vet ./internal/...
   go test ./internal/...
   cd frontend && npx tsc --noEmit
   ```

4. Try the change in the running app (`wails dev`). For UI changes, check both light and dark themes.
5. Open a pull request against `main` and fill in the template.

## Project conventions

- **Go**: format with `gofmt`. Backend code lives in `internal/`; methods exposed to the UI are bound in `app.go`. Wrap errors with context and never panic on bad remote data.
- **Frontend**: TypeScript with React function components and Tailwind CSS v4. Reuse the existing components in `frontend/src/components` (including the confirm dialog from `ConfirmContext`) rather than adding native `window.confirm`/`alert`.
- **Generated code**: `frontend/wailsjs/` is generated by Wails. After changing exported methods or types in Go, run `wails dev` or `wails generate module` and commit the result.
- **Security**: never log passwords, passphrases, or private key contents.
- **Tests**: add tests for new backend logic where practical (see `internal/updater/updater_test.go`).

## Commit messages

We use [Conventional Commits](https://www.conventionalcommits.org/):

```
feat(ports): persist port forwards with connection profiles
fix(sftp): avoid nil dereference when the session is closed
docs: clarify Linux build dependencies
```

Common types: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `ci`.

## Pull request checklist

- [ ] The change is focused and the PR description explains *why*
- [ ] `gofmt`, `go vet`, `go test`, and `tsc --noEmit` pass
- [ ] Tested manually, with notes or screenshots for UI changes
- [ ] Docs and `RELEASE_NOTES.md` updated if user-visible behavior changed

A maintainer will review as soon as possible. Small, focused PRs get merged fastest.

## Releases

Maintainers cut releases by pushing a `v*` tag, which triggers the [release workflow](.github/workflows/release.yml). The version lives in `internal/version`, `wails.json`, and `frontend/package.json`; keep them in sync.
